The project

From choosing a build to recording a run

ReapKeep is my largest independent project. I own the gameplay programming, game design, interface, and development tools, with a planned PC release on Steam.

A run connects several kinds of state: the selected character and starting weapon, the build assembled through upgrades, rules introduced by Death’s Decrees, and progress that survives after the run ends. My work includes both the individual mechanics and the code that keeps those transitions consistent.

This case study follows those connections through the C# implementation. Source code remains private.

Connected architecture

How the game fits together

The central boundary is between authored definitions, state that belongs to the current run, and progress saved for later. Managers coordinate updates across those boundaries.

Authored definitions

Weapon stats, evolution recipes, UI availability, and stage settings are described by reusable assets.

Current-run state

Inventories, calculated stats, Decrees, and counters change while playing and reset for a new session.

Persistent records

Run history and stage/difficulty completion records carry selected results beyond the current scene.

Architecture scope and startup details

This diagram groups systems rather than showing every class or dependency. Arrows represent selected calls, events, or data reads—not a universal event bus. BootstrapManager creates missing persistent managers, while SceneController applies scene configuration. Several managers independently subscribe to Unity’s scene events. Death’s Decrees also has a separate scene bootstrap.

01 · Weapon evolutions

A new weapon without losing the build

The system separates recipe eligibility from the inventory operation that performs an evolution.

Three recipe types, one coordinated flow

WeaponEvolution assets describe the ingredients, required levels, result, and consumption rules. The manager checks the current inventory and selected character before allowing a route.

That supports weapon-and-item recipes, two-weapon combinations, and character-specific starting-weapon evolutions without embedding each recipe in a menu script.

Preserving the primary weapon slot

The inventory either reuses the existing runtime weapon or creates the evolved prefab. It validates the replacement before renaming the inventory entry, keeps the primary weapon’s position in the runtime list, and refreshes its UI, stats, and history entry.

The manager then handles optional ingredient consumption, records discovery, and raises the evolution event.

Gameplay example

A two-weapon recipe can combine two occupied slots into one evolved weapon, while a signature route can evolve the selected character’s assigned starter without requiring an item.

Weapon + item

Checks the item’s required level. The recipe controls whether the item is consumed.

Weapon + weapon

Checks both weapons. Consuming the secondary ingredient can free its inventory slot.

Signature starter

Requires the matching character and assigned starter. The level threshold is authored in the recipe.

Implementation detail: deferring an automatic evolution

An inventory-change event can fire while an upgrade is still being completed. The evolution manager sets a pending flag and checks signature evolutions during its next Update(), with a re-entry guard around the operation. This avoids replacing the weapon inside the inventory-change callback itself.

Signature routes default to level 7 in code, but the route asset controls the threshold. The replacement has validation guards; it is not a general rollback transaction for every possible exception.

  • WeaponS/Evolutions/Core/WeaponEvolutionManager.cs — IsEligible(), EvolveCore(), and HandleWeaponInventoryChanged().
  • WeaponS/UI/PlayerWeaponInventory.cs — TryEvolveWeapon().

02 · Interface architecture

Menus have a lifecycle, too

Opening a submenu involves more than visibility: the system also needs to manage interaction, navigation focus, and pause ownership.

A stack for navigation, configuration for availability

UIConfiguration defines which panels a scene allows, opens by default, and prewarms. UIManager manages the open-panel stack, transitions, and restoration of the panel underneath.

A covered panel can remain initialized while its rendering and input are disabled. On return, the manager restores its state and initializes navigation focus.

Pause follows the stack

PauseOnPanelActive listens for panel changes and checks whether a configured pause-causing panel remains anywhere in the stack. It holds a pause token while that condition is true, even when another menu covers the pause screen.

Player-facing behavior

Open Options from Pause, change a setting, then go back. The underlying Pause panel can remain in the stack, so navigating through the submenu does not itself resume combat.

Inactive construction

UIPrefabHub creates panels under an inactive staging parent, then registers them while still inactive. An active prefab does not briefly display or accept input during registration.

Selective prewarming

Configured panels initialize sequentially while hidden. Default-active panels skip that pass; other panels return inactive by default after warming, so their hidden update methods do not continue running.

Implementation references and configuration

The stack example describes supported behavior, not a recorded playtest. Soft-disable, covered-panel retention, prewarming, and pause-causing panel types are configurable. Rendering dormancy disables canvases, raycasters, CanvasGroup interaction, and menu navigation; it does not inherently stop every script on an active object.

  • UI/Core/UIManager.cs — OpenPanelAnimated(), RestorePanelAsTop(), MakePanelRenderDormant(), and PrewarmPanelsForScene().
  • UI/Core/UIConfiguration.cs and UI/Core/UIPrefabHub.cs.
  • UI/Menus/PauseAndGameOver/PauseOnPanelActive.cs — stack inspection and pause-token ownership.

03 · Runs and progression

A result is more than a game-over screen

Session state, historical records, and unlock progress have different responsibilities and lifetimes.

Start with the selected run context

The run controller reads the selected stage and difficulty, configures the clock, and begins a history entry with the selected character. The session-start event resets live run counters; the scoring manager avoids replacing a history entry that is already active.

Finalize once, then present the result

At the end of a run, GameManager reads the stage controller’s victory flag and asks ScoreManager to finalize. The scoring manager reads the live counters and clock, builds a score breakdown, and sends the result to run history. Guards in both managers prevent repeated finalization calls.

On victory, the selected stage and difficulty also receive a completion record. The summary panel can display the saved score alongside run statistics.

Progression example

Clearing one difficulty does not mark every difficulty in that realm complete. Stage access and difficulty access check their own authored prerequisites against the stored completion records.

Implementation references and current boundaries

Reaching the stage’s configured victory time sets a victory flag. A stage may finish immediately or enter its configured terminator phase. These are supported code paths, not a claim about every stage asset.

Stage completion uses a stable stageId:difficultyId key. Run history and the profile are separate stores; they are not saved as one atomic transaction. Profile loading includes migration and clamping, but does not currently restore a backup automatically after primary-file corruption.

Combat foundations

The calculations and lifecycles underneath

Build changes depend on predictable stat calculation, explicit updates, and reusable actors.

04 · Weapon stat pipeline

Modifier order is part of the design

Weapons can respond differently to player stats, but build-defining item effects still need to apply at their intended strength.

I calculate damage, cooldown, and critical chance from the authored level row, apply player modifiers, then blend that influence using each weapon’s scaling weights. Runtime item effects and Decree weapon modifiers come afterward.

Why this matters: a weapon with low player-stat scaling does not also dilute those later item effects. Recalculation starts from authored values rather than repeatedly multiplying an already-modified result.

Implementation detail and references

Adding a modifier requires choosing its place in the calculation. Individual weapons can extend the core pipeline through before/after hooks.

  • WeaponS/Core/WeaponConfig.cs — level rows and per-stat scaling weights.
  • WeaponS/Core/Weapon.cs — RecomputeRuntimeStats().
  • WeaponS/Core/WeaponManager.cs — player modifiers, runtime item effects, and final weapon doctrine modifiers.
  • Player/Stats/Pipeline/PlayerStatsPipeline.cs and Player/Core/Player.cs — player stat construction and refresh notifications.

05 · Death’s Decrees

One choice, several kinds of update

Death’s Decrees alter the current run. Offers exclude active duplicates, incompatible groups, and weapon doctrines that are not relevant to the player’s build. Granting or replacing a Decree also checks those constraints.

After a change, the manager rebuilds combined modifiers from neutral values. Player stats and weapons are recalculated; existing enemies refresh their scaling while preserving their current health ratio.

Why this matters: the change affects the run already in progress, not only newly spawned actors. The HUD receives a change event, while difficulty calculations read the current spawn-rate and population multipliers when needed.

Gameplay example

A rule that changes enemy health can rescale enemies already on screen without restoring them all to full health.

Implementation detail and references

The manager uses direct calls for actor updates and an event for the HUD; difficulty calculations read current modifier values. Refreshing existing enemies uses a scene-wide lookup, making crowded encounters a useful profiling target.

  • Systems/DeathsDecrees/Runtime/DeathsDecreeManager.cs — BuildOffer(), Grant(), Replace(), CommitChange(), and RefreshAllRuntimeConsumers().
  • Systems/DeathsDecrees/Runtime/DeathsDecreeRuntimeModifiers.cs — current aggregated multipliers.
  • StagesAndRuns/RunFlow/Difficulty/HexManager.cs — spawn-rate and maximum-alive multiplier reads.
  • Systems/DeathsDecrees/UI/DeathsDecreeHud.cs — subscribes to ActiveDecreesChanged.

06 · Enemy pooling

Prepare the next life before enabling it

Reusing an enemy is more than hiding and showing its GameObject. A previous life can leave changed scale, visual state, or combat configuration behind.

The dedicated enemy pool prepares each instance while inactive: it restores configured visual state, sets its position and rotation, and applies any supplied base-stat override before activation. Pool callbacks run next; a global freeze, if active, is applied afterward so those callbacks do not reset it.

Why this matters: Unity activation callbacks see the prepared location and configuration. A guarded return path avoids returning the same instance twice, and configurable creation budgets limit how much runtime growth the pool permits in a frame.

Implementation detail and references

EnemyPool is separate from the generic BasePool<T> and legacy pooler. Visual reset and creation limits are configurable. Object reuse does not establish an allocation-free frame or a measured FPS improvement.

  • Enemies/Pooling/EnemyPool.cs — SpawnEnemy(), Despawn(), cached visual state, and runtime creation limits.
  • Shared/Pooling/Core/BasePool.cs — separate generic pooling infrastructure with optional staged warmup.
  • Shared/Pooling/Components/PoolLink.cs — generic-pool ownership and lifecycle callback support.

Development tools

Tools built alongside the game

Importing balance data, inspecting recipe problems, and capturing comparable run data are part of the development workflow.

Validate weapon tables before applying them

The weapon CSV importer has separate validation and apply modes. It matches rows to weapon configurations and levels; applying changes records Unity Undo state and updates the data assets. Blank cells can leave existing values unchanged.

Implementation reference and validation scope

WeaponS/Editor/WeaponStatsCsvImporter.cs

Validation covers supported input and mapping checks, not every possible semantic or balance problem.

Compare difficulty with a shared upgrade plan

A benchmark runner automates difficulty passes using a shared seeded upgrade plan. It checks replay failures and exports a CSV timeline with enemy population, pressure, damage, progression, movement, and frame-rate samples.

Implementation references and measurement scope

DebugTools/Automation/Benchmarking/DifficultyBenchmarkRunner.cs

DebugTools/Automation/Benchmarking/DifficultyBenchmarkTelemetry.cs

The shared plan controls upgrade choices, not the full Unity simulation. No measured performance results are claimed here; the frame-rate field is a sample, not a percentile benchmark.

Audit evolution routes without changing assets

A read-only editor window scans recipe assets for invalid references, duplicate routes, reversed weapon combinations, and stable-ID collisions. It also reports routes outside the runtime Resources discovery path and missing result presentation assets. Findings can be selected or pinged in Unity, or copied into a report.

Implementation reference

WeaponS/Editor/WeaponEvolutionRouteAuditWindow.cs — ScanProject() and the route, ID, and presentation checks.

Additional implementation notes

Composable achievement rules

AchievementRule combines AchievementConditionSO assets with All/Any logic, allowing authored conditions to be reused across rules instead of giving every achievement a separate hard-coded check.
