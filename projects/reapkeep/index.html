Overview

Building a full game, not only a prototype

ReapKeep is my largest independent project. I own its design, programming, content pipeline, interface, balancing tools, technical documentation, and release planning. A typical run lasts 15 minutes and combines automatic combat with character mechanics, evolving weapons, escalating encounters, and Death’s Decrees that alter the rules of the current run.

The central engineering goal is to keep those systems expandable. New weapons, items, enemies, rewards, and encounters are authored through data rather than being hard-coded into individual scenes.

Engineering deep dives

The systems behind the run

These examples are drawn from the current Unity project and show how I approach scalability, iteration, validation, and runtime performance.

01 · Content pipeline

Author once, validate, then run

Weapons, items, enemies, characters, achievements, and spawn phases are represented as reusable data assets. Custom Unity windows import balancing tables, validate required fields, build related assets, and audit evolution routes before content reaches a playtest.

  • CSV validation can run without modifying assets
  • Per-level weapon rows feed centralized runtime calculations
  • Audit tools detect incomplete or conflicting configurations

02 · Automated verification

Repeatable balance tests instead of guesswork

A deterministic benchmark runner executes AI-controlled passes across multiple difficulty levels. It preserves the same seeded upgrade plan between runs and writes a detailed CSV timeline for comparison.

  • Records enemy pressure, damage, progression, movement, and FPS
  • Tracks upgrade-sequence hashes and failed replay plans
  • Supports accelerated runs, invulnerability, and defined end conditions

03 · Cross-system design

Death’s Decrees change rules safely

Completing structures periodically produces filtered Decree offers. The manager removes duplicates, incompatible groups, and irrelevant weapon doctrines; accepted Decrees are limited to four and can later be replaced.

After a selection, the system rebuilds combined modifiers and refreshes player stats, weapons, enemies, spawning, HUD state, and specialized behaviors.

04 · Runtime performance

High-volume combat without constant allocation

A reusable generic pooling layer supports enemies, projectiles, effects, and pickups. Pools can warm gradually, grow in batches, enforce capacity limits, and expose active, inactive, and total-created counts for diagnostics.

  • Lifecycle callbacks reset state when objects enter or leave a pool
  • Staged warmup distributes creation work across frames
  • Spawn telemetry tracks caps, overflow, recycling, and despawning

Technical challenge

Keeping hundreds of interactions understandable

Reverse bullet-hell games quickly combine many weapons, upgrades, enemies, modifiers, and UI states. A change that looks isolated can affect several systems at once.

I addressed this by separating authored data from runtime state, centralizing stat recalculation, using reusable effects and interfaces, and building inspection tools alongside the gameplay features. This makes iteration faster and reduces the risk of silent balance or configuration errors.
