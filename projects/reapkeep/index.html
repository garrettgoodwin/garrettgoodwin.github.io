Overview

Making a growing set of systems work together

ReapKeep is my largest independent project. As its solo developer, I work across gameplay programming, game design, UI, content authoring, and development tools.

The engineering challenge is interaction: a new item can change weapon behavior, a Decree can affect enemies already on screen, and a recycled enemy must start its next life in a clean state. These are three examples of how I handle those boundaries.

The walkthrough below is based on the current C# implementation. The game is still in development; source code remains private.

Architecture

Authored data, runtime state, explicit updates

ScriptableObjects describe content. Runtime systems calculate the current state. Direct calls and targeted events connect gameplay changes to their consumers.

Engineering deep dives

Three decisions in the implementation

Each example connects a gameplay requirement to its data flow, update order, and tradeoffs.

01 · Weapon stat pipeline

Modifier order is part of the design

Weapons can respond differently to player stats, but build-defining item effects still need to apply at their intended strength.

I calculate damage, cooldown, and critical chance from the authored level row, apply player modifiers, then blend that influence using each weapon’s scaling weights. Runtime item effects and Decree weapon modifiers come afterward.

Why this matters: a weapon with low player-stat scaling does not also dilute those later item effects. Recalculation starts from authored values rather than repeatedly multiplying an already-modified result.

The order is explicit and inspectable, but adding a modifier means deciding where it belongs—not just appending another multiplier.

  • WeaponS/Core/WeaponManager.cs — player modifiers, runtime item effects, and final weapon doctrine modifiers.
  • Player/Stats/Pipeline/PlayerStatsPipeline.cs and Player/Core/Player.cs — player stat construction and refresh notifications.

02 · Death’s Decrees

One choice, several kinds of update

Death’s Decrees alter the current run. Offers exclude active duplicates, incompatible groups, and weapon doctrines that are not relevant to the player’s build. Granting or replacing a Decree also checks those constraints.

After a change, the manager rebuilds combined modifiers from neutral values. Player stats and weapons are recalculated; existing enemies refresh their scaling while preserving their current health ratio.

Why this matters: the change affects the run already in progress, not only newly spawned actors. The HUD receives a change event, while difficulty calculations read the current spawn-rate and population multipliers when needed.

This uses both direct calls and events. Refreshing existing enemies currently includes a scene-wide lookup, so that path deserves profiling during crowded encounters.

Implementation references
  • Systems/DeathsDecrees/Runtime/DeathsDecreeManager.cs — BuildOffer(), Grant(), Replace(), CommitChange(), and RefreshAllRuntimeConsumers().
  • Systems/DeathsDecrees/Runtime/DeathsDecreeRuntimeModifiers.cs — current aggregated multipliers.
  • StagesAndRuns/RunFlow/Difficulty/HexManager.cs — spawn-rate and maximum-alive multiplier reads.
  • Systems/DeathsDecrees/UI/DeathsDecreeHud.cs — subscribes to ActiveDecreesChanged.

03 · Enemy pooling

Prepare the next life before enabling it

Reusing an enemy is more than hiding and showing its GameObject. A previous life can leave changed scale, visual state, or combat configuration behind.

The dedicated enemy pool prepares each instance while inactive: it restores configured visual state, sets its position and rotation, and applies any supplied base-stat override before activation. Pool callbacks run next; a global freeze, if active, is applied afterward so those callbacks do not reset it.

Why this matters: Unity activation callbacks see the prepared location and configuration. A guarded return path avoids returning the same instance twice, and configurable creation budgets limit how much runtime growth the pool permits in a frame.

Enemy pooling is its own implementation. The project also contains a generic BasePool<T> and a legacy pooler; these are not one universal pool. Reuse reduces repeated creation, but does not establish an allocation-free frame or a measured FPS gain.

Implementation references
  • Enemies/Pooling/EnemyPool.cs — SpawnEnemy(), Despawn(), cached visual state, and runtime creation limits.
  • Shared/Pooling/Core/BasePool.cs — separate generic pooling infrastructure with optional staged warmup.
  • Shared/Pooling/Components/PoolLink.cs — generic-pool ownership and lifecycle callback support.

Development tools

Making changes easier to inspect

Content tooling supports authoring; automated runs help gather evidence for balancing. Neither substitutes for playtesting.

Validate weapon tables before applying them

The weapon CSV importer has separate validation and apply modes. It matches rows to weapon configurations and levels; applying changes records Unity Undo state and updates the data assets. Blank cells can leave existing values unchanged.

Validation helps catch supported input and mapping problems. It is not a guarantee that every combination is balanced or valid.

Implementation reference

WeaponS/Editor/WeaponStatsCsvImporter.cs

Compare difficulty with a shared upgrade plan

A benchmark runner automates difficulty passes using a shared seeded upgrade plan. It checks replay failures and exports a CSV timeline with enemy population, pressure, damage, progression, movement, and frame-rate samples.

This controls part of the comparison, not the entire Unity simulation. No measured performance results are claimed here; the frame-rate field is a sample, not a percentile benchmark.

Further implementation notes

Beyond combat

A few supporting systems, with their current boundaries.

Startup and scene ownership

BootstrapManager creates missing persistent managers. SceneController handles scene configuration and scene notifications; GameManager signals run lifecycle changes. Some managers subscribe to Unity scene events independently. Death’s Decrees has a separate scene bootstrap, so it is not simply another persistent bootstrap entry.

Versioned profile persistence

ProfileSaveStore loads JSON, runs migration and clamping logic, and writes through a temporary file. Updating an existing save attempts file replacement with a backup, with a copy/move fallback. The current load path does not automatically recover from that backup; handling a corrupt primary save is an area for further hardening.

Composable achievement rules

AchievementRule combines AchievementConditionSO assets with All/Any logic, allowing authored conditions to be reused across rules instead of giving every achievement a separate hard-coded check.

Technical notes reviewed against the September 2026 script snapshot. Scene and prefab configuration, compiled behavior, and profiler results are outside the scope of this code walkthrough.
